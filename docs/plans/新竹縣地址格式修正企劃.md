# 新竹縣地址格式修正企劃

日期：2026-10-13。同日依政府來源檔核對結果修訂。

本企劃處理新竹縣路檔的門牌格式問題。2026-10-13 `taiwan-lvr-geodata` 擁有者決定：修正在本專案的資料來源端進行，下游不另加解析規則。修正完成並更新版本後，下游重新釘選本專案的提交。

## 問題

固定版本 `3ff9be0265b22a4910abf2bd4e3e96c7653fb6f0` 中，新竹縣（縣市代碼 `10004`）262,762 列門牌全部無法依下游地址規則建立地址鍵。範例 `FULL_ADDR`：`新竹縣竹北市中興里7鄰19之8I-`。兩個特徵：

- 門牌主號後沒有「號」。
- 結尾多出一個大寫英文字母加連字號，目前看到 `I-`、`G-`、`H-`。

其他 21 個縣市的路檔沒有這個字母格式。證據見[已知問題](../known-issues.md)「新竹縣地址格式」。

## 來源核對結果

以下事實由主代理於 2026-10-13 下載政府檔案核對取得。下載檔放在暫存目錄，沒有加入 Git。

### 來源與檔案

- 資料集 172380（data.gov.tw）。`modifiedDate` 為 2026-05-06 13:06:49。說明寫明 1150305 產製。
- 同一版本有 4 種格式，網址前段相同：`https://ws.hsinchu.gov.tw/001/Upload/1/opendata/8774/2663/03e34b18-f513-46f5-a561-6940cac83712`，副檔名為 `.xlsx`、`.csv`、`.xml`、`.json`。
- 宣告編碼：CSV 為 BIG5，其他為 UTF-8。
- SHA-256：

| 格式 | 大小 | SHA-256 |
| --- | --- | --- |
| CSV | 22.8 MB | `f75d63efd665ba8f8aded414b53898a209d653479e568494e5f76acbdc386ddc` |
| JSON | 78.6 MB | `06842e70289f93abeedebadc4487191946443892b07084adc4e976abf70bb376` |
| XLSX | 11.1 MB | `f57737cc43efbbe6216a718dad290e1744c1eefaaeff68209805ec2a62444dd2` |

### 原因

- 更新器對新竹縣使用預設 `fmt="csv"`。
- 字母來自政府 CSV 本身，不是更新器誤接欄位。CSV 原始位元組就是英文字母，例如 `I-` 是 `0x49 0x2D`。標題列的「號」正常（Big5 `B8B9`）。
- 對應關係：鄰 → `D-`、巷 → `G-`、弄 → `H-`、號 → `I-`。
- 同一版本的 JSON 與 XLSX 都是正常單位字。JSON 的號、巷、弄分別是標準碼位 U+865F、U+5DF7、U+5F04。U+865F 共出現 262,775 次。
- CSV 只能用 big5hkscs 解碼，用 big5 或 cp950 都會失敗。
- CSV 另有第二個缺陷：Big5 以外的字被換成「?」。共 8,668 列含「?」。

### CSV 與 JSON 逐欄比對

兩檔都是 262,762 列，順序相同。

| 欄位 | 不同列數 | 把 `G-`、`H-`、`I-` 換回單位字後仍不同 |
| --- | --- | --- |
| 號 | 262,761 | 1 |
| 巷 | 89,550 | 0 |
| 弄 | 26,969 | 0 |
| 村里 | 7,039 | 7,039 |
| 地區 | 1,599 | 1,081 |
| 街或路段 | 618 | 618 |

換回單位字後，剩下的差異都是 Big5 以外的字變成「?」：舘 4,748、鷄 1,954、犂 613、焿 589、磜 354、猪 200、廍 128、邨 73、私用區 U+E397 63、横 7、U+2015 5、蔴 1、脚 1、私用區 U+EA05 1。

號欄那 1 列是來源自身的資料問題。JSON 的號欄是整段地址「五峰鄉竹林村001鄰２３之３號」，CSV 顯示 `001D-`。

### XLSX 與 JSON 比對

- XLSX 只有一張工作表「工作表2」。11 個標題與 CSV 相同：省市縣市代碼、鄉鎮市區代碼、村里、鄰、街或路段、地區、巷、弄、號、橫座標、縱座標。
- 262,762 列中只有 13 列不同，都在號欄。差異是開頭多了全形空白 U+3000，例如「　　　１０１號二樓」。
- Python 的 `str.strip()` 會去掉 U+3000。更新器的 `normalize()` 用的就是 `str.strip()`。

### 本機路檔現況

`roads/10004-*.csv`（固定版本 `3ff9be0`，`update_log.csv` 記 2026-06-14）：

- 262,762 列，與政府來源列數相同。
- `NUMBER` 欄沒有任何「號」。`I-` 出現 262,775 次。另有 `G-` 3 次、`D-` 1 次。
- `LANE` 欄有 `G-` 89,552 次。`ALLEY` 欄有 `H-` 26,969 次。
- 7,588 列的 `FULL_ADDR` 含「?」。
- 13,946 列的 `VILLAGE` 以 `-000` 結尾，表示村里沒有對上代碼。

### 原待查問題的答案

1. 字母的意義：是政府 CSV 匯出時把單位字換成字母。證據是原始位元組，以及同版 JSON 與 XLSX 都是正常字。這是事實。
2. 受影響欄位：`NUMBER`、`LANE`、`ALLEY` 都受影響。`FULL_ADDR` 由這些欄位組成，所以一起出錯。這是事實。
3. 是否每版重現：2026-05 版有。本機 6 月路檔與這一版一致。以後的版本是否還有，目前不知道。改用 XLSX 後不再依賴 CSV 匯出，所以不需要先回答這一題。

### 推論（未驗證）

- 13,946 列村里未對上，可能有一部分是「?」造成的，例如「上?里」。`area_2014.csv` 已同時收「新竹縣竹東鎮上舘里」與「上館里」、「鷄林里」與「雞林里」。改用 XLSX 後未對上的列數應會下降，但不一定降到 0。7,039 與 13,946 的差額原因未查。

## 修正方案

把 `COUNTIES["新竹縣"]` 改為 `fmt="xlsx"`，保留資料集 172380。這是唯一的程式行為改動。

選這個方案的理由：

- 同一版本的 XLSX 與 JSON 只差 13 列，而且差異會被現有的 `normalize()` 去掉。
- 更新器已有 XLSX 讀取路徑，雲林縣與金門縣正在使用。不需要新增讀取器。
- XLSX 檔案最小。JSON 要新增讀取器，而且檔案大 7 倍。
- 不用字串規則把字母換回單位字。那種做法修不了「?」，也會在來源某天改正後變成錯誤。

已確認不受影響的部分：

- `get_download_urls()` 依 `resourceFormat` 過濾，改成 xlsx 後只會選到 XLSX 那一份。
- 新舊判斷用資料集的 `modifiedDate`，與格式無關。

## 風險與注意事項

- **每月排程不會自動重跑新竹縣。** 來源 `modifiedDate` 是 2026-05-06，早於 `update_log.csv` 的 2026-06-14。`--updated-only` 不會選到新竹縣。修正後必須手動執行 `python scripts/update_addresses.py 新竹縣`。
- **XLSX 數字儲存格。** 代碼與鄰可能是數字儲存格。`read_xlsx_rows()` 會把整數浮點數轉成不帶 `.0` 的字串。新竹縣的鄉鎮市區代碼是 7 碼且不以 0 開頭，不受前導零問題影響。若號、巷、弄欄出現純數字儲存格，會失去全形數字，但結果經 `normalize()` 後相同。驗收要實際檢查，不只依推論。
- **只修開頭與結尾的 U+3000。** 欄位中間若有 U+3000 會保留。目前比對只看到開頭有。
- **私用區字元原樣保留。** U+E397（63 次）與 U+EA05（1 次）在來源中就是私用區字元。本企劃不轉換，列為未決事項。
- **路檔檔名會變。** 原本含「?」的路名在檔名中被換成 `_`。改用 XLSX 後檔名會改成真實字。`road.csv` 由 `build_road_index` 重建，不需手改。
- **號欄塞整段地址的 1 列。** 保留來源原值，不寫特例。

### H-3 測試清單

合成 XLSX 用 openpyxl 在測試內產生。測試只呼叫 `read_xlsx_rows()`、`normalize()` 與設定值，不呼叫 `run()`。

1. `COUNTIES["新竹縣"].fmt == "xlsx"`，`dataset_id == 172380`。
2. 數字儲存格：鄉鎮市區代碼 `1000401`、鄰 `7` 以數字寫入，讀回為字串 `"1000401"`、`"7"`，沒有 `.0`。
3. U+3000：號欄寫入「　　　１０１號二樓」，經 `normalize()` 後為「101號二樓」。
4. Big5 以外的字：村里寫入「上舘里」、街或路段寫入「犂頭店」，讀回原字，不含「?」。

不寫端到端下載測試。不寫 CSV 字母還原測試，因為不再走 CSV。

### H-4 資料驗收

全部以重跑後的 `roads/10004-*.csv` 計算：

- 總列數為 262,762，或與當次下載檔列數相符。若來源已改版，記錄新列數與 SHA-256。
- `NUMBER`、`LANE`、`ALLEY` 欄符合 `[A-Z]-$` 的列數為 0。
- `NUMBER` 欄不含「號」的列逐列列出，並與 XLSX 原值比對一致。不含「號」的列不得多於 XLSX 原檔號欄不含「號」的列。
- `FULL_ADDR` 含「?」或 U+FFFD 的列數為 0。
- `VILLAGE` 以 `-000` 結尾的列數低於 13,946。記錄實際數字，不要求 0。
- 抽 5 列與 XLSX 原列逐欄比對，結果一致。
- `git diff --stat` 中，其他縣市的路檔沒有任何改動。

## 未決事項

1. 私用區字元 U+E397 與 U+EA05 要不要對應成標準字。需要來源機關的造字表，本企劃不處理。
2. 村里未對上的剩餘列數。H-4 執行後才知道。若仍大量未對上，另立工作。
3. 其他縣市的「?」。主代理掃描本機全部路檔，`FULL_ADDR` 含「?」或 U+FFFD 的列數：彰化縣 `10007` 19,524、屏東縣 `10013` 6,297、臺東縣 `10014` 2,018、花蓮縣 `10015` 420、高雄市 `64` 181、新北市 `65` 17、`10002` 10、金門縣 `09020` 2、臺北市 `63` 2、雲林縣 `10009` 1。這些數字尚未與各縣來源比對。字母加連字號的格式只在 `10004` 出現。這一項不在本企劃範圍，已另開[缺字還原企劃](缺字還原企劃.md)。該企劃查明「?」是政府匯出時把 Big5 以外的字換掉，並用官方清單還原。

## 不做

- 不在下游 `taiwan-lvr-geodata` 加去尾或補「號」的解析規則。
- 不用字串規則把 `G-`、`H-`、`I-` 換回單位字。
- 不手改路檔。
- 不新增 JSON 讀取器。
- 本企劃不新增執行期品質檢查（例如「?」比例上限）。這屬於第 3 項未決事項的範圍。

## 下游影響

修正前，下游離線索引沒有新竹縣有效門牌，新竹縣交易只能靠 TGOS 定位。修正後下游要重新釘選版本並重跑離線階段。
